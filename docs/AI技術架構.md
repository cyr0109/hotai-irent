# AI 技術架構

> 本文整理自團隊內部技術文件，狀態以 7 月中的實測為準。App 端原型已完成，模型端多半是**實驗驗證**，尚未串成正式服務。

## 三個環節

```
用戶拍照（取車 / 還車）
   │
   ▼
【環節一】即時防呆   拍照當下攔住不堪用的照片    → 合格照片 + 品質 meta
   │
   ▼
【環節二】還車 AI 辨識   新車損比對 + 車內整潔度  → 車況報告（附信心度）
   │
   ▼
【環節三】後台預警與人工複核   派工 / 清潔 / 維修
```

設計原則：**AI 的每個判斷都附信心度，信心不足就交給人工複核，不強行自動判定。**

## 環節一：即時防呆

| 檢查 | 做法 | 狀態 |
|---|---|---|
| 手機姿勢（橫拿） | 手機陀螺儀，姿勢不對快門直接失效 | 原型已實作 |
| 模糊 | Laplacian 變異數＋對比度正規化（夜間照片誤擋率 66% → 11%） | 已實作、已用真實照片校準 |
| 光線不足／全黑 | 平均亮度，門檻取自照片亮度分佈的自然斷點 | 已實作 |
| 車牌入鏡 | YOLO 車牌偵測，信心度 0.15 ＋「車牌框須落在車身框內」濾掉背景車牌 | 已實測 |
| 太遠／太近 | 車身佔畫面比例＋車身被畫面邊緣切到幾個方向 | 已實作 |
| 拍攝角度 | MobileNetV3-small 四類分類（左前／右前／左後／右後），再看四角是否齊全 | 訓練資料品質是瓶頸，原型為 mock |

兩個關鍵決策（詳見 [docs/adr/](adr/)）：
- **硬擋只放在快門層**。照片內容的問題（模糊、角度、車牌）一律軟提示，使用者可選擇跳過。
- **拍照鎖橫式**。真正的問題是方向不一致，不是方向本身。

## 環節二：還車 AI 辨識

**新車損比對**

```
借／還照片 → ORB 確認角度相同 → 車身覆蓋率 → YOLO 車損偵測 → 信心度過濾 → 面積正規化
          → 借還嚴重度比較 → AI Agent（Hotai GPT）複核 → 套用環節一光線信心度
```

- 偵測 6 類：凹痕、刮痕、裂痕、玻璃碎裂、燈損、爆胎。
- 比較邏輯：還車分數超過借車的 1.3 倍視為新增或惡化；出現新類別視為新車損。
- ORB 比對發現取還車角度對不上，或 YOLO 信心度不夠，直接交給 AI Agent（和泰自架機房的 Hotai GPT，基於 Qwen3-VL fine-tune）同時看兩張照片判斷。
- 夜間或低光照片會降級為「建議人工複核」，不自動判定。

**車內整潔度**：髒污／普通／乾淨三分類，輕量分類器或 Hotai GPT zero-shot 二選一。

## 分層推論：省成本

不是每張照片都丟給多模態大模型：

1. **第一層（約九成案例）**：CV／CNN／YOLO 小模型秒判，信心高就直接輸出。
2. **第二層（灰色地帶）**：信心落在模糊區間的才升級給 Hotai GPT 二次確認。

## 實測下來學到的

- **照片方向**要在拍照源頭防，不能事後猜。真實歷史照片有相當比例是躺著的，事後用車框長寬比或車牌比例都不可靠。
- **訓練資料品質**比模型選型重要。部位分類器準確率卡在 46%，人工抽查發現旋轉、內容與標籤對不上、畫質不可用佔了大宗，改走人工篩選一批小而乾淨的資料。
- **車損 recall 有缺口**：凹痕 recall 約 0.52。各類別閾值與 1.3 倍門檻都是暫定值，上線前要用更多樣本校準。
