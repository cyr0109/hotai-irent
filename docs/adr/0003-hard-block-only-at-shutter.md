# 硬擋只保留在快門層，照片內容問題一律降為軟提示

**狀態**：accepted（擴大 ADR 0001 的適用範圍）

**背景**：`CONTEXT.md` 原本把環節一的防呆分成兩級：模糊、角度錯誤、太遠太近、鏡頭髒污屬「硬擋」（擋下拍照、不允許跳過），低光源、車牌缺漏、角度沒拍全屬「軟提示」（可跳過）。ADR 0001 已針對角度覆蓋與車牌完整性選擇了軟提示路線；重新檢視後，硬擋清單裡的其他項目其實適用完全相同的論證。

**決策**：
1. 硬擋只發生在**快門層**——手機物理姿勢與規定方向不符時快門直接失效，使用者根本按不下去。因此 UI 上不存在「拍了但不算數、強制重拍」這個狀態。
2. 所有**照片內容層級**的問題（模糊、角度錯誤、太遠太近、鏡頭髒污、低光源、車牌缺漏、角度沒拍全）一律降為軟提示：建議重拍，但可跳過，跳過即進入合併免責聲明。
3. 取車 4 張方向照改為**必拍**（移除現行流程圖上「已確認車況正常，同意使用，選擇略過拍照」的整組跳過入口）——張數硬性、內容不硬性。

**為什麼**：
- 「擋下已經拍好的照片並強制重拍」是流程裡最挫折的互動；而使用者在狹窄停車格、車後被遮擋、夜間路邊等情境下，往往**物理上就是拍不出合格照片**，硬擋只會把人卡死在原地（與 ADR 0001 同一論證）
- 快門層硬擋沒有這個問題：轉個手機就能解除，成本趨近於零，而且它擋掉的是唯一一種會直接讓後端辨識失效的錯誤（側躺影像）
- 張數必填能保證環節二**永遠有基準照可比對**——沒有基準照，新車損前後比對整條主線就不成立；而內容不合格至少還能降級成單張絕對偵測（`progress.md` 技術驗證顯示單張偵測仍可抓到 crack conf=0.84）
- 免責聲明保留了舉證力：使用者被具體告知缺了什麼、仍選擇繼續，這比一張被強迫重拍到合格、卻讓使用者中途放棄租車的照片更有價值

**後果**：環節二的輸入品質下限降低，pipeline 必須容忍模糊、缺角度、無車牌的照片，並在訂單上標記缺項，讓客服調閱時知道這筆訂單的證據強度。
